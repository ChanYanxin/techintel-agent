# 项目面试讲解提纲（据实说明 MVP 阶段）

## 60 秒版本

我实现了面向科研资料问答和实验表格分析的多 Agent 工作流 MVP。编排使用 LangGraph，分为规划、检索、分析、验证、报告节点。检索是可复现的 BM25 RAG，源 ID 在回答中可追踪。分析工具有两个可选后端：Python 本地逻辑和 TypeScript MCP stdio 服务端；系统会显示实际走了哪条路径。工具失败最多尝试两次，然后携带告警进入最终报告，不会默默假装成功。重要流程可在 LangGraph interrupt 节点等待人工批准。FastAPI 提供 REST、SSE 与浏览器演示页，附带测试与离线评测脚本。

## 面试官会追问

**为什么这么设计？** 任务只有检索/数值分析两类，采用可审计、确定性的规划路由，减少自由规划的不稳定性。虽有多个功能性节点，这个 MVP 不声称存在自主协商的 LLM 多 Agent 群体。

**为什么不是纯 LangChain Agent？** LangGraph 显式图结构使重试、条件路由、人工 interrupt、Checkpointer 状态恢复容易追踪。未来把 Planner 替换成 LLM 结构化输出不改变验证节点。

**MCP 与 Tool calling 的区别？** MCP 是标准化工具发现/调用协议；模型 tool calling 是模型提出结构化的动作请求。当前应用的工具调用由工作流节点决定，通过 MCP ClientSession 真正跨语言调用 Node 工具，不冒充模型自行决策。

**怎样防止幻觉？** 数据集含来源 ID、用证据限制生成并检测未知引用 ID；但仅验证 ID 并不保证段落语义事实正确，后续需要人工标注数据和 Faithfulness/groundedness 评测。

**评测怎么做？** 现在只有人工撰写的同源 synthetic 检索测试，Hit@3 / 负例拒答 / median latency 仅是局部工程回归指标；没有生产任务成功率、业务提升幅度或用户流量。

**主要局限？** 没有生产级持久化、身份认证或真正的大规模论文数据，没有验证远程 LLM/MCP 运行；只用于验证架构与核心异常场景，下一步真实数据、嵌入检索、持久化、鉴权、成本 P95 对照实验。
